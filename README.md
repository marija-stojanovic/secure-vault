# Secure Vault

Secure Vault is a zero-knowledge web application for securely storing and sharing sensitive information such as passwords, API keys, and certificates. It was developed as a security-focused academic project and demonstrates how modern authentication, client-side cryptography, session protection, intrusion detection, and tamper-evident auditing can be combined in a full-stack system.

The application supports three roles: **Admin**, **Team Lead**, and **Developer**.

## Key Features

- Create, view, update, rotate, and soft-delete encrypted secrets.
- Share secrets with other users through hybrid envelope encryption.
- Role-based authorization for Admin, Team Lead, and Developer accounts.
- Local authentication with mandatory TOTP multi-factor authentication.
- Google OpenID Connect login with local TOTP as an additional factor.
- Rotating access and refresh tokens stored in secure cookies.
- Configurable password, session, failed-login, and secret-rotation policies.
- API Gateway with Redis-backed rate limiting and suspicious-IP blocking.
- Honeytokens and a controlled SQL injection demonstration endpoint.
- Append-only, hash-chained audit records with integrity verification.
- HTTPS communication between the SPA, API Gateway, and backend.

## Security Highlights

### Client-Side Encryption

Secret encryption and decryption happen exclusively in the browser through the Web Crypto API. A key derived from the user's master password with **PBKDF2-SHA-256** protects the user's private key. Every secret is encrypted with a fresh **AES-256-GCM** data key, while **RSA-OAEP-3072** is used to wrap that key for its owner and authorized recipients.

The master password and plaintext secret content are never sent to the server. The backend stores only ciphertext, initialization vectors, public keys, encrypted private-key material, and wrapped data keys.

### Multi-Factor Authentication

Local authentication uses two steps:

1. username and Argon2-hashed login password verification;
2. a six-digit RFC 6238 TOTP code generated by an authenticator application.

Google OIDC login is also followed by the application's own TOTP verification. TOTP codes are protected against replay, and encrypted TOTP seeds are stored separately from Vault encryption material.

## Architecture

```text
React SPA (HTTPS :5173)
          |
          v
Spring Cloud API Gateway (HTTPS :8443)
          |
          v
Spring Boot REST API (HTTPS :8444, localhost only)
          |
          +-- MySQL 8     persistent application data
          +-- Redis       rate limiting and intrusion counters
```

All browser API traffic goes through the Gateway. The backend is bound to the local interface and is not directly exposed to the network in the development configuration.

## Getting Started

### Prerequisites

- Java 21
- Maven 3.9+ or the included Maven Wrapper
- Node.js and npm
- MySQL 8
- Redis, or Memurai on Windows
- A Google OAuth client only if Google sign-in will be tested

### 1. Create the Database

Run the SQL scripts as a MySQL administrator in this order:

```text
database/secure_vault_schema.sql
database/restrict_application_user_privileges.sql
database/create_honeypot_demo_user.sql
```

The runtime account is intentionally limited to `SELECT`, `INSERT`, `UPDATE`, and `DELETE`. Hibernate uses `ddl-auto=validate` and does not modify the database schema.

### 2. Trust the Development Certificate Authority

Generate or inspect the development certificates in the `certificates` directory, then install `secure-vault-dev-ca.crt` into the current user's **Trusted Root Certification Authorities** store.

The included helper can be executed from PowerShell when local script execution is allowed:

```powershell
.\certificates\install-dev-ca.ps1
```

These certificates are intended for local development only.

### 3. Configure Optional Google OIDC

Set the Google client secret before starting the backend:

```powershell
$env:GOOGLE_CLIENT_SECRET="your-google-client-secret"
```

The configured redirect URI in Google Auth Platform must be:

```text
https://localhost:8443/login/oauth2/code/google
```

Local username/password authentication works without Google OIDC configuration.

### 4. Start the Backend

```powershell
cd backend
.\mvnw.cmd spring-boot:run
```

The backend listens internally on `https://127.0.0.1:8444`.

### 5. Start the API Gateway

Open a second terminal:

```powershell
cd gateway
mvn spring-boot:run
```

The Gateway is available at `https://localhost:8443`.

### 6. Start the Frontend

Open a third terminal:

```powershell
cd frontend
npm ci
npm run dev
```

Open the application at:

```text
https://localhost:5173
```

## Tests

Run backend tests:

```powershell
cd backend
.\mvnw.cmd test
```

Run Gateway tests:

```powershell
cd gateway
mvn test
```

Build the frontend:

```powershell
cd frontend
npm ci
npm run build
```

## Important Notes

- Development certificates and local configuration values must be replaced with managed secrets and trusted certificates before production deployment.
- The local MySQL connection is not TLS-enabled because the database runs on the same development machine.
- The SQL injection endpoint exists only for the controlled honeypot demonstration and must not be enabled in production.
- The current project models a single shared development team; multi-team organization can be added as a future extension.

## Project Context

This project was developed for the Internet Security course at the Faculty of Electrical Engineering, University of Banja Luka. Its purpose is to demonstrate secure software design and defense-in-depth rather than serve as a production-ready secret-management service.
